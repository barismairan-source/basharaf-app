# ثبت ورود و خروج پرسنل با اینترنت مغازه

وضعیت (۲۹ مهر ۱۴۰۵):
- نسخهٔ اول (IP مغازه و لینک شخصی) روی main و لیارا منتشر شده است. migration اول اجرا شده و آزمون جعل IP روی سایت واقعی پاس شده است.
- نسخهٔ دوم (تأیید با Face ID یا اثر انگشت، گزارش بازه‌ای و خروجی CSV) روی شاخهٔ `feat/attendance-clock` است. **migration دوم و انتشار آن هنوز انجام نشده‌اند.**

## چطور کار می‌کند

۱. مدیر IP ثابت هر شعبه را در «منابع انسانی ← زمان و حضور ← ورود با مودم» ثبت می‌کند. دکمهٔ «IP همین‌جا را نشان بده» را وقتی داخل مغازه و روی وای‌فای مغازه است بزند تا IP را همان‌طور که سرور می‌بیند ببیند.

۲. برای هر نفر «ساخت لینک» می‌زند. لینک یا QR را **حضوری** روی گوشی خود آن نفر باز می‌کند. لینک **یک‌بارمصرف** است و ۷۲ ساعت مهلت دارد. با اولین باز شدن، یک کلید جدا فقط روی همان گوشی ذخیره می‌شود (کوکی httpOnly). اگر همان لینک روی گوشی دیگری باز شود، کار نمی‌کند.

۳. اگر «Face ID» روشن باشد (پیش‌فرض روشن است)، همان بار اول در صفحهٔ گوشی دکمهٔ «فعال‌سازی Face ID / اثر انگشت» می‌آید. یک بار زده می‌شود و گوشی صورت یا انگشت صاحبش را می‌خواهد.

۴. پرسنل هر روز صفحهٔ زیر را باز می‌کنند:

`/clock`

دکمهٔ «ثبت ورود» یا «ثبت خروج» را می‌زنند و با Face ID یا اثر انگشت تأیید می‌کنند. ثبت **فقط** وقتی پذیرفته می‌شود که:
- درخواست از IP ثبت‌شدهٔ یکی از شعبه‌ها آمده باشد. با اینترنت موبایل، VPN روشن یا از خانه رد می‌شود.
- گوشی همان گوشی فعال‌شده باشد.
- اگر Face ID روشن است، صاحب گوشی تأیید کرده باشد.

۵. ساعت ثبت از ساعت دیتابیس گرفته می‌شود، نه از گوشی. پایین صفحه، ورود و خروج‌های امروز همان نفر نشان داده می‌شود.

۶. با هر خروج، یک ردیف **پیش‌نویس** در تب «ثبت حضور» ساخته می‌شود و اگر برای آن روز شیفت برنامه‌ریزی‌شده باشد، به نزدیک‌ترین شیفت وصل می‌شود. تأیید و حقوق دقیقاً مثل قبل است و هیچ‌چیز خودکار تأیید نمی‌شود. اگر ساختن پیش‌نویس ممکن نباشد، مثلاً کارمند نرخ ساعتی ندارد یا با حضور دیگری هم‌پوشانی دارد، رویداد ثبت می‌ماند و در پنل «نیاز به ثبت دستی» نشان داده می‌شود.

## Face ID / اثر انگشت

- از استاندارد WebAuthn (passkey) استفاده می‌شود. Safari در آیفون از iOS 14 و Chrome در اندروید از آن پشتیبانی می‌کنند.
- **هیچ دادهٔ بیومتریکی به سرور نمی‌رسد.** گوشی خودش صورت یا انگشت را بررسی می‌کند و فقط یک امضای دیجیتال می‌فرستد. سرور فقط کلید عمومی را نگه می‌دارد.
- ثبت حضور به **هر دو** نیاز دارد: کلید گوشی (کوکی) و امضای Face ID. پس اگر passkey به گوشی دیگری منتقل یا به اشتراک گذاشته شود (مثلاً با AirDrop)، به‌تنهایی کافی نیست.
- هر امضا یک‌بارمصرف است و فقط برای همین سایت معتبر است.
- اگر Face ID چند بار رد شود، گوشی **رمز قفل خودش** را می‌خواهد. پس کسی که رمز گوشی را بداند هم می‌تواند تأیید کند.
- **تنظیم سراسری:** در همان تب، کارت «Face ID / اثر انگشت» یک کلید روشن و خاموش دارد. اگر خاموش باشد، فقط گوشی فعال‌شده و اینترنت مغازه لازم است.
- **استثنای فردی:** برای گوشی قدیمی که Face ID یا اثر انگشت ندارد، در فهرست پرسنل «استثنای Face ID» بزنید. با ساخت لینک جدید، استثنا حفظ می‌شود.
- تعویض گوشی یا ثبت دوبارهٔ Face ID فقط با «لینک جدید» از مدیر ممکن است.
- اگر دامنهٔ سایت عوض شود (مثلاً به `basharaf.meeez.me`)، Face ID هر نفر باید یک بار دوباره فعال شود، چون passkey به نام دامنه بسته است.
- **آیفون:** اگر صفحه را از آیکن صفحهٔ اصلی (Add to Home Screen) باز کنند، آن آیکن حافظهٔ جدا از Safari دارد و ممکن است گوشی را «فعال‌نشده» نشان دهد. صفحه در این حالت راهنمایی نشان می‌دهد. ساده‌ترین راه: همان صفحه در Safari باز شود یا نشانک (Bookmark) شود.

## گزارش

- بازهٔ تاریخ (حداکثر سه ماه)، فیلتر شعبه و فیلتر نفر.
- برای هر ثبت: مدت حضور و نشان Face ID.
- جمع ساعت هر نفر در بازه. این عدد فقط ورود و خروج‌های کامل را می‌شمارد؛ مبنای حقوق نیست و حقوق از حضور تأییدشده حساب می‌شود.
- دکمهٔ «خروجی CSV» که در اکسل با فارسی درست باز می‌شود.

## قواعد فنی (قاعدهٔ حقوقی نیستند)

- ورود دوباره بدون خروج رد می‌شود. خروج بدون ورود هم رد می‌شود.
- خروج کمتر از یک دقیقه بعد از ورود رد می‌شود، چون به‌احتمال زیاد لمس اشتباه است.
- ورودی که بیش از ۱۶ ساعت باز بماند «ناقص» حساب می‌شود. خروج روی آن ثبت نمی‌شود و مدیر دستی ثبت می‌کند. ورود جدید مجاز است.
- لمس دوباره یا تلاش دوباره با همان کلید، فقط یک ثبت می‌سازد. دو لمس هم‌زمان پشت سر هم اجرا می‌شوند (قفل ردیف پرسنل).
- تأخیر، ارفاق، گرد کردن و اضافه‌کاری در این ماژول **نیستند**. ثانیه‌ها فقط کنار گذاشته می‌شوند، چون ستون‌های فعلی `HH:MM` هستند.
- این عددها در `lib/attendance-clock/rules.ts` تعریف شده‌اند و قابل تغییرند.

## چه چیزی ذخیره می‌شود

- رویداد خام فقط افزودنی است. یک trigger در دیتابیس جلوی حذف و بازنویسی آن را می‌گیرد، از جمله نشان «تأیید با Face ID». اصلاح در ردیف حضور انجام می‌شود و رویداد خام به‌عنوان سابقهٔ اصلی می‌ماند.
- IP خام پرسنل در رویداد ذخیره **نمی‌شود**. فقط «کدام IP ثبت‌شدهٔ شعبه» تطبیق خورد ذخیره می‌شود.
- ثبت‌های ردشده، مثل خارج از شبکه، IP نامطمئن یا Face ID ناموفق، با IP در `audit_log` ثبت می‌شوند. تغییر تنظیم Face ID و استثناها هم ثبت می‌شوند.
- از لینک و کلید گوشی فقط هش SHA-256 در دیتابیس هست. از Face ID فقط کلید عمومی passkey ذخیره می‌شود.
- GPS، مشخصات دستگاه، عکس و هیچ دادهٔ بیومتریکی ذخیره نمی‌شود.

## دسترسی

- تنظیم IP، ساخت یا لغو لینک، کلید Face ID و استثناها: مجوز `hr.attendance.clockSetup`. پیش‌فرض آن فقط مدیر کل است و از پنل دسترسی‌ها قابل اعطاست.
- دیدن ورود و خروج‌ها و گزارش: `hr.attendance.view`. مدیر شعبه فقط شعبهٔ خودش را می‌بیند.

## راه‌اندازی نسخهٔ دوم (Face ID) — به ترتیب

۱. backup از دیتابیس بگیرید.

۲. این migration را در pgAdmin اجرا کنید. اجرای دوباره‌اش امن است و به داده‌های قبلی دست نمی‌زند:

`project-docs/migrations/db-attendance-clock-faceid.sql`

۳. **فقط بعد از آن** کد را merge و push کنید. کد جدید ستون‌های تازه را می‌خواند؛ اگر کد زودتر برود، ثبت حضور تا اجرای migration کار نمی‌کند.

۴. بعد از انتشار، Face ID پیش‌فرض روشن است. پس هر کس که گوشی‌اش از قبل فعال است، با اولین باز کردن صفحه یک بار «فعال‌سازی Face ID» می‌زند. اگر می‌خواهید فعلاً بدون Face ID باشد، کلید را در پنل خاموش کنید.

## راه‌اندازی نسخهٔ اول (انجام شده)

۱. migration `project-docs/migrations/db-attendance-clock.sql` اجرا شد.

۲. کد منتشر شد. آزمون جعل IP روی سایت واقعی پاس شد: سرور سرآیندهای ساختگی `X-Real-IP` و `X-Forwarded-For` را نادیده گرفت.

۳. IP ثابت هر شعبه ثبت می‌شود. IP داخلی مودم مثل `192.168…` پذیرفته نمی‌شود؛ IP عمومی لازم است.

## آزمون‌های انجام‌شده

- **آزمون واحد** در `tests/unit/attendanceClock.test.ts`: استخراج IP پشت پراکسی، جعل سرآیند، CIDR در IPv4 و IPv6، ارقام فارسی، ترتیب ورود و خروج، وقت تهران، شیفت شبانه، و نشانی سایت برای Face ID پشت پراکسی.
- **روی Postgres واقعی محلی (نه production):**
  - هر دو migration دوبار اجرا شدند، migration دوم روی داده‌های موجود. ستون‌ها و قیدها با schema درایزل یکی‌اند.
  - ۲۵ سناریوی سرتاسری HTTP با Face ID خاموش پاس شد.
  - با یک «Face ID نرم‌افزاری» که دقیقاً مثل گوشی امضا می‌کند، این‌ها آزموده شد:
    - ثبت بدون تأیید صاحب گوشی رد می‌شود.
    - امضای جعلی رد می‌شود.
    - امضای سایت دیگر رد می‌شود.
    - امضای تکراری رد می‌شود.
    - امضای درست ولی خارج از شبکه رد می‌شود.
    - passkey بدون کلید گوشی رد می‌شود.
    - ثبت دوبارهٔ Face ID بدون لینک جدید رد می‌شود.
    - تلاش دوباره پس از قطع شبکه فقط یک ثبت می‌سازد.
    - استثنای فردی و کلید سراسری درست کار می‌کنند.
    - شمارندهٔ امضا جلو می‌رود.
- آزمون با Face ID واقعی آیفون فقط روی سایت واقعی ممکن است، چون passkey نشانی واقعی سایت (https) را لازم دارد.

## محدودیت‌ها

- اگر IP ثابت شعبه عوض شود، تا وقتی مدیر IP جدید را ثبت نکند ثبت حضور کار نمی‌کند. پیام صفحه همین را می‌گوید.
- کسی که هم گوشی و هم رمز قفل گوشی همکارش را داشته باشد و داخل مغازه باشد، می‌تواند جای او ثبت کند.
- اگر اینترنت مغازه قطع باشد، ثبت ممکن نیست. مدیر از تب «ثبت حضور» دستی ثبت می‌کند.
- جدول‌ها هنوز `organization_id` ندارند (طرح «میز»). هنگام اجرای آن طرح، این سه جدول هم باید اضافه شوند. trigger فقط‌افزودنی هنگام backfill ستون جدید باید موقتاً غیرفعال شود.
