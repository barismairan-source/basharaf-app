## ۰. خلاصه‌ی مدیریتی (یک‌دقیقه‌ای)

کد از نظر فنی سالم است: کامپایل، تست‌ها و build همه سبزند و بخش‌های حساسی مثل «تأیید تراکنش» و «تأیید برگه‌ی انبار»
درست قفل شده‌اند. ولی **۷ مشکل جدی** پیدا شد:

1. **دسترسی‌ها فقط در ظاهر برنامه اعمال می‌شوند، نه در سرور.** هر کاربر واردشده (حتی آشپز) می‌تواند از طریق API کدملی،
   شماره‌شبا و آدرس همه‌ی پرسنل، فیش حقوق همه، و تراکنش‌ها/گزارش‌های همه‌ی شعب را بخواند.
2. **کاربر غیرفعال‌شده یا نقش‌عوض‌شده تا ۳۰ روز همچنان به API دسترسی دارد.**
3. **ثبت دوباره با دوبار کلیک/تکرار درخواست** در ۵ نقطه‌ی مالی: حذف تراکنش، رد/تأیید هم‌زمان، «تحویل شد» سفارش،
   دریافت سفارش خرید، برگشت ثبت حقوق ← موجودی صندوق/انبار برای همیشه به‌هم می‌ریزد.
4. **ستون «موجودی» صفحه‌ی انبار عدد غلط نشان می‌دهد** (بعد از هر تأیید برگه به عدد قبلی برمی‌گردد). 🔎
5. **سود و زیان، هزینه‌ی مواد را دوبار حساب می‌کند** (یک‌بار موقع خرید، یک‌بار موقع فروش).
6. **حساب کاربری مشتری آنلاین عملاً کار نمی‌کند:** کد ورود (OTP) هرگز پیامک نمی‌شود و سفارش‌ها به حساب مشتری وصل نمی‌شوند.
7. **محدودکننده‌ی تلاش (rate limit) مشترک و دورزدنی است:** چند رزرو از وای‌فای رستوران، ورود کارکنان را ۳۰ دقیقه قفل می‌کند؛
   و مهاجم با یک هدر جعلی محدودیت حدس رمز را دور می‌زند.

به‌علاوه: Next.js و چند کتابخانه آسیب‌پذیری امنیتی شناخته‌شده دارند (۱ بحرانی، ۵ بالا)، دوره‌ی مالی «بسته» واقعاً قفل نیست،
ساعت سرور احتمالاً UTC است (بین ۰۰:۰۰ تا ۰۳:۳۰ «امروز» اشتباه حساب می‌شود)، و برنامه در هر بار باز شدن **همه‌ی** تراکنش‌ها را دانلود می‌کند.

## ۱. باگ‌ها

### 🔴 B1 — دسترسی بخش‌ها و قابلیت‌ها فقط در UI است، API فقط «لاگین بودن» را چک می‌کند

**چه می‌شود:** middleware فقط صفحه‌ها را بر اساس دسترسی بخش محدود می‌کند (`matcher` عمداً `/api` را رد می‌کند).
اکثر APIها فقط `requireSession()` دارند و فیلتر شعبه را فقط برای نقش `BranchUser` اعمال می‌کنند؛ نقش‌های `Chef` و `Warehouse`
(که در ساخت کاربر *اجباراً* به یک شعبه وصل‌اند) در API مثل مدیر کل «همه‌ی شعب» را می‌بینند.

نمونه‌های تأییدشده با خواندن کد:

| داده | مسیر | گارد فعلی |
|---|---|---|
| کدملی، شبا، شماره‌حساب، آدرس همه‌ی پرسنل | `GET /api/employees`، `GET /api/employees/[id]` | فقط لاگین (`lib/payroll/employeeSerializer.ts` همه را برمی‌گرداند؛ قابلیت `hr.people.viewSensitive` فقط در UI چک می‌شود) |
| نرخ ساعتی هر نفر | `GET /api/employees/[id]/hourly-rates` | فقط لاگین |
| فیش حقوق همه (خالص/ناخالص/کسورات) | `GET /api/payroll/runs`، `GET /api/payroll/runs/[id]`، `GET /api/payroll/events` | فقط لاگین |
| همه‌ی تراکنش‌های همه‌ی شعب | `GET /api/transactions` | فیلتر فقط برای BranchUser |
| گزارش مالی/خروجی اکسل | `/api/reports`، `/api/reports/flash`، `/api/reports/drilldown`، `/api/export` | فیلتر فقط برای BranchUser |
| دفتر هر صندوق و هر طرف‌حساب | `/api/accounts/[id]/ledger`، `/api/contacts/[id]/ledger` | بدون هیچ فیلتر شعبه |
| چک‌ها | `/api/cheques`، `/api/cheques/[id]` (GET بدون چک شعبه) | فیلتر فقط برای BranchUser |
| فهرست همه‌ی کاربران با ایمیل و موبایل | `GET /api/users` | فقط لاگین |
| ثبت تراکنش برای هر شعبه | `POST /api/transactions` | Chef/Warehouse محدودیت شعبه ندارند (وضعیت pending می‌شود) |

همچنین از ۱۹ قابلیت `hr.*` که در پنل دسترسی نمایش داده می‌شوند، **فقط یکی** (`hr.systemAccess.manage`) در سرور چک می‌شود؛
قابلیت‌های `settings.*` هم فقط تب را نشان/پنهان می‌کنند (APIهایشان `requireAdmin` است). یعنی دادن/گرفتن این دسترسی‌ها
در عمل اثری ندارد و پنل دسترسی گمراه‌کننده است.

**راه‌حل:** یک helper واحد سمت سرور (مثلاً `requireSection(session, 'transactions')` + `branchScope(session)`)
که **هر نقش غیر SuperAdmin** را به شعبه‌ی خودش محدود کند و در همه‌ی routeها استفاده شود؛ اطلاعات حساس پرسنل فقط با
`hr.people.viewSensitive` برگردد؛ قابلیت‌های `hr.*` واقعاً در APIهای HR چک شوند. یک تست ماتریسی (نقش × مسیر) جلوی برگشت این مشکل را می‌گیرد.

### 🔴 B2 — کاربر غیرفعال/نقش‌عوض‌شده تا ۳۰ روز به API دسترسی دارد

`requireSession()` (`lib/auth/session.ts`) فقط امضای JWT را چک می‌کند و نقش/شعبه/دسترسی را از داخل توکن ۳۰ روزه می‌خواند.
فقط middleware (برای صفحه‌ها) و `/api/auth/me` دیتابیس را چک می‌کنند. پس:
- کارمندی که اخراج و غیرفعال شده، با همان کوکی تا ۳۰ روز می‌تواند API را صدا بزند.
- مدیری که از SuperAdmin به BranchUser تنزل داده شده، در API تا ۳۰ روز همچنان SuperAdmin است.
- تغییر رمز هم نشست‌های قبلی را باطل نمی‌کند.

**راه‌حل:** ستون `token_version` روی users (با هر غیرفعال‌سازی/تغییر نقش/تغییر رمز +۱ شود) و چک آن در `requireSession` (با کش چندثانیه‌ای)،
یا کوتاه‌کردن عمر توکن + refresh.

### 🔴 B3 — ثبت دوباره با دوبار کلیک یا تکرار درخواست (۵ نقطه‌ی مالی)

الگوی مشترک: وضعیت رکورد **بیرون از تراکنش دیتابیس و بدون قفل** خوانده می‌شود و بعد اثر مالی اعمال می‌شود.
اگر دو درخواست هم‌زمان برسند (دوبار لمس روی موبایل، retry شبکه، دو مدیر هم‌زمان)، هر دو از چک عبور می‌کنند.

| کجا | نتیجه‌ی دو درخواست هم‌زمان |
|---|---|
| حذف تراکنش — `app/api/transactions/[id]/route.ts` (DELETE) | موجودی صندوق/طرف‌حساب/انبار **دو بار** برگردانده می‌شود ← drift دائمی |
| رد تراکنش — `app/api/transactions/[id]/reject/route.ts` | UPDATE فقط `WHERE id` دارد؛ اگر هم‌زمان تأیید شود، تراکنش «ردشده» می‌شود ولی مبلغش در صندوق می‌ماند (و حذف بعدی هم برش نمی‌گرداند) |
| «تحویل شد/تکمیل» سفارش بیرون‌بر — `lib/ordering/orders.ts` → `transitionOrderStatus` | دو تراکنش فروش + دو بار کسر انبار + دو سند COGS |
| دریافت سفارش خرید — `app/api/purchase-orders/[id]/receive/route.ts` | دو رسید انبار، دو برابر شدن موجودی، دو بدهی به تأمین‌کننده |
| برگشت ثبت حقوق — `lib/payroll/postToBasharaf.ts` → `reversePayrollPost` | مبلغ حقوق دو بار به صندوق برمی‌گردد |

(مسیرهای «تأیید تراکنش» و «تأیید برگه‌ی انبار» و «تأیید حقوق» درست با `FOR UPDATE` قفل شده‌اند — الگوی درست در خود پروژه هست.)

**راه‌حل:** در همه، خواندن را داخل `db.transaction` با `.for('update')` ببرید یا UPDATE را شرطی کنید
(`WHERE status = <وضعیت مورد انتظار> RETURNING` و اگر ردیفی برنگشت ← 409). در UI هم دکمه‌ها حین درخواست غیرفعال شوند.

### 🔴 B4 — «موجودی» نمایش‌داده‌شده‌ی انبار با واقعیت فاصله می‌گیرد 🔎

انبار دو عدد دارد: `qty_physical` (لایه‌ی فیزیکی، هنگام ثبت برگه) و `qty_base` (موجودی قطعی، هنگام تأیید).
- `approveVoucherTx` (`lib/db/inventoryHelpers.ts`) اول اثر فیزیکی را **برمی‌گرداند** و بعد فقط `qty_base` را تغییر می‌دهد؛
  هیچ جایی `qty_physical` را دوباره با موجودی قطعی هم‌تراز نمی‌کند (جز انبارگردانی). نتیجه: بعد از تأیید یک خرید ۱۰ کیلویی،
  `qty_physical` به عدد قبل از خرید برمی‌گردد.
- رسید سفارش خرید (`purchase-orders/[id]/receive`) و کسر خودکار فروش منو فقط `qty_base` را تغییر می‌دهند.
- ولی ستون **«موجودی»** صفحه‌ی اقلام انبار (`app/(app)/inventory/items/page.tsx`)، صفحه‌ی نیمه‌آماده‌ها، **پیشنهاد خرید**
  (`/api/purchase-orders/suggestions`) و گزارش **کمبود موجودی** (`/api/inventory/reports/exceptions`) همه از `qty_physical` استفاده می‌کنند.

اثر: عدد موجودی روی صفحه و هشدار کمبود/پیشنهاد خرید فقط بعد از هر انبارگردانی درست است و با هر تأیید از واقعیت دور می‌شود.
**راه‌حل:** بعد از اعمال اثر قطعی، `qty_physical` را هم به همان اندازه حرکت دهید (یا تعریف را ساده کنید: موجودی نمایشی = `qty_base` + جمع برگه‌های pending).
کوئری تأیید در بخش ۵.

### 🔴 B5 — سود و زیان هزینه‌ی مواد اولیه را دو بار حساب می‌کند

- هر خرید مواد (`postPurchaseToAccounting` و رسید سفارش خرید) یک تراکنش **هزینه** با دسته‌ی «خرید مواد اولیه» می‌سازد.
- هر فروش با رسپی متصل (هر سفارش بیرون‌بر تحویل‌شده در `lib/ordering/orderAccounting.ts` و هر فروش منو در تأیید تراکنش)
  یک تراکنش **هزینه‌ی COGS** دیگر برای *همان مواد* می‌سازد.
- `app/api/reports/route.ts` (و `lib/reports/flashReport.ts`) هر دو را در «هزینه» جمع می‌زند:
  `otherExpense = expense - cogs - payroll` ← خرید مواد در «سایر هزینه‌ها» می‌ماند و COGS هم جدا کم می‌شود ← **سود خالص کمتر از واقع**.

**راه‌حل (تصمیم حسابداری لازم است):** یا خرید مواد «دارایی انبار» باشد و در P&L فقط COGS بیاید (و خرید فقط در گزارش جریان نقد)،
یا COGS خودکار ساخته نشود. پیشنهاد: اولی (استاندارد تعهدی) + گزارش جریان نقد جدا.

### 🔴 B6 — حساب کاربری مشتری آنلاین کار نمی‌کند

- `createWebOtp` (`lib/ordering/webCustomer.ts`) کد را فقط در دیتابیس ذخیره می‌کند؛ در production **هیچ پیامکی ارسال نمی‌شود**
  (فقط در حالت توسعه در کنسول چاپ می‌شود) و `/api/customer/auth/send-otp` هم چیزی نمی‌فرستد. پس هیچ مشتری‌ای نمی‌تواند وارد شود.
- صفحه‌ی checkout `orderCustomerId` را می‌فرستد ولی schema مسیر `/api/public/order/create` آن را ندارد (zod حذفش می‌کند)
  و `linkOrderToWebCustomer` هیچ‌جا صدا زده نمی‌شود ← «سفارش‌های من» همیشه خالی است.
- ⚠️ هنگام رفع، `orderCustomerId` را **از کوکی نشست مشتری** بخوانید نه از body (وگرنه هر کسی سفارش را به حساب دیگری می‌چسباند).

### 🔴 B7 — محدودکننده‌ی تلاش مشترک و قابل‌دورزدن

`lib/auth/rateLimit.ts` یک Map حافظه‌ای دارد که **هم لاگین** و هم رزرو عمومی (ثبت/پیگیری/لغو)، ثبت فرم استخدام و آپلود رزومه
از آن استفاده می‌کنند — و این مسیرها حتی برای درخواست *موفق* `recordFailedAttempt` صدا می‌زنند.
- ۵ رزرو/آپلود از یک IP (مثلاً وای‌فای رستوران یا یک خانواده) ← **ورود کارکنان از همان IP ۳۰ دقیقه قفل**.
- IP از اولین مقدار `X-Forwarded-For` خوانده می‌شود که کلاینت می‌تواند جعل کند ← محدودیت حدس رمز لاگین با عوض‌کردن هدر دور زده می‌شود.
- اگر پشت پروکسی لیارا این هدر نباشد، همه «unknown» می‌شوند ← یک مهاجم کل لاگین را قفل می‌کند. 🔎

**راه‌حل:** limiterهای جدا برای هر مسیر؛ برای مسیرهای عمومی شمارش «درخواست» نه «شکست»؛ IP از آخرین hop قابل‌اعتماد پروکسی؛
برای لاگین علاوه بر IP، شمارش بر اساس ایمیل.

`isDateInClosedPeriod` فقط در ویرایش/حذف تراکنش (`app/api/transactions/[id]/route.ts`) چک می‌شود. ثبت تراکنش جدید با تاریخ گذشته،
تأیید تراکنش pending، ایمپورت اکسل، ثبت خودکار سفارش/انبار/ضایعات/حقوق و برگشت حقوق همه می‌توانند در ماهِ بسته بنشینند.
همچنین تاریخ یک تراکنش approved (که در ماه باز است) را می‌شود به داخل یک ماه بسته **منتقل** کرد (چک فقط روی تاریخ قبلی است).

### 🟠 M2 — تاریخ‌ها سمت سرور یکسان‌سازی نمی‌شوند
فرمت استاندارد پروژه `۱۴۰۵/۰۲/۳۱` (ارقام فارسی، دو رقمی) است و گزارش‌ها با **مقایسه‌ی متنی** فیلتر/گروه‌بندی می‌کنند
(`gte/lte` روی `date` و `SUBSTRING(date,1,7)`). ولی:
- ایمپورت اکسل تراکنش/انبار (`isValidJalaliString`) ارقام لاتین و بدون صفر (`1405/3/6`) را قبول و **همان‌طور ذخیره** می‌کند ←
  این ردیف‌ها از گزارش‌های بازه‌ای جا می‌افتند و ماهشان در نمودار جدا/غلط می‌آید.
- `POST /api/transactions` و چند مسیر دیگر `date: z.string().min(1)` دارند (هر رشته‌ای).
**راه‌حل:** یک تابع `normalizeJalali()` در مرز همه‌ی APIها + یک migration یک‌باره برای اصلاح داده‌های موجود (کوئری بخش ۵).

### 🟠 M3 — «امروز» با ساعت سرور حساب می‌شود (احتمالاً UTC) 🔎
`getTodayJalali()` و `new Date().toISOString().slice(0,10)` در سرور در ۱۵+ مسیر استفاده می‌شوند (تاریخ سفارش آنلاین، تولید تسک‌های امروز،
داشبورد، گزارش flash، انبارگردانی، دریافت سفارش خرید، شمارش HR…). اگر سرور UTC باشد، از ۰۰:۰۰ تا ۰۳:۳۰ تهران «امروز» = دیروز است —
دقیقاً ساعت‌های پرکار آخر شب رستوران. خود پروژه برای رزرو `lib/reservations/tehranTime.ts` را ساخته ولی بقیه از آن استفاده نمی‌کنند.
**ساده‌ترین راه‌حل:** متغیر محیطی `TZ=Asia/Tehran` روی اپ لیارا.

### 🟠 M4 — ایمپورت اکسل تراکنش‌ها ضد تکرار ندارد
`app/api/transactions/import/route.ts` ردیف‌ها را مستقیم `approved` و با اثر روی صندوق ثبت می‌کند. آپلود دوباره‌ی همان فایل = دو برابر شدن
همه‌ی موجودی‌ها. چک دوره‌ی بسته هم ندارد. **راه‌حل:** هش فایل/ردیف + پیش‌نمایش قبل از ثبت.

### 🟠 M5 — «برگه‌ی اصلاحی» خرید، پول را برنمی‌گرداند
`/api/inventory/vouchers/[id]/reversal` برای خرید یک برگه‌ی خروج می‌سازد؛ تأیید آن کالا را کم می‌کند ولی تراکنش هزینه‌ی خرید و کسر صندوق
دست‌نخورده می‌ماند (و خروج با میانگین موزون فعلی قیمت‌گذاری می‌شود نه قیمت خرید اصلی).

### 🟠 M6 — حذف فروش منو، انبار «شبح» می‌سازد
در `lib/inventory/menuSaleDeduction.ts` اگر موجودی کم باشد، `issueConfirmed` فقط مقدار موجود را کسر می‌کند، ولی `deductionLines` و
`inv_stock_tx` مقدار **درخواستی** را ثبت می‌کنند. حذف بعدی آن فروش، مقدار درخواستی را به انبار برمی‌گرداند ← موجودی بیشتر از واقع.

### 🟠 M7 — رسپی سراسری در شعبه‌ی دیگر 🔎
اقلام انبار شعبه‌ای‌اند (`inv_items.branch_id`) ولی رسپی سراسری (`branchId=null`) به یک قلم مشخص اشاره می‌کند؛ فروش در شعبه‌ی ب
ممکن است از انبار شعبه‌ی الف کم کند. اگر فقط یک شعبه انبار دارد، فعلاً بی‌اثر است.

### 🟠 M8 — پرداخت آنلاین سفارش
- `/api/public/order/pay/request` برای سفارش لغوشده/ردشده هم لینک پرداخت می‌سازد (چک وضعیت ندارد) ← پول گرفته می‌شود، مسیر استرداد نیست.
- callback در صورت خطای شبکه‌ی verify دوم، `paid` را به `failed` بازنویسی می‌کند (UPDATE بدون شرط).
- سفارش آنلاینی که پرداختش ثبت نشده ولی «تحویل شد» زده شود، هرگز در حسابداری ثبت نمی‌شود و بعداً هم ثبت نمی‌شود.
- هر بار درخواست پرداخت، `payAuthority` قبلی را جایگزین می‌کند؛ پرداخت موفق از تب قبلی پیدا نمی‌شود.
- `callbackUrl` از `req.url` ساخته می‌شود؛ پشت پروکسی ممکن است دامنه/پروتکل داخلی باشد 🔎 — بهتر از `NEXT_PUBLIC_APP_URL`.

### 🟠 M9 — چک‌ها به حسابداری وصل نیستند
وصول/برگشت چک (`/api/cheques/[id]` PATCH) فقط وضعیت را عوض می‌کند؛ هیچ تراکنش/اثری روی صندوق یا طرف‌حساب ندارد. کاربر شعبه
می‌تواند `branchId` چک را به شعبه‌ی دیگر تغییر دهد.

### 🟠 M10 — «ریست کارخانه» موجودی‌ها را صفر نمی‌کند
`/api/settings/wipe` جدول تراکنش‌ها را TRUNCATE می‌کند ولی `accounts.balance` و `contacts.balance` می‌مانند ← بعد از ریست، صندوق‌ها
موجودی دارند بدون هیچ تراکنشی. به‌علاوه `TRUNCATE … CASCADE` هر جدولی را که به این‌ها FK دارد (سفارش‌ها، سفارش‌های خرید، …) هم
پاک می‌کند در حالی که پاسخ API فهرست محدودتری را اعلام می‌کند. هیچ پشتیبان‌گیری قبل از اجرا گرفته نمی‌شود.

### 🟠 M11 — نمودار ماهانه‌ی گزارش بعد از ۲ سال ماه‌های قدیمی را نشان می‌دهد
`app/api/reports/route.ts`: `ORDER BY … ASC LIMIT 24` ← وقتی داده بیش از ۲۴ ماه شود، **قدیمی‌ترین** ۲۴ ماه نمایش داده می‌شود.

### 🟠 M12 — رمز فراموش‌شده: هیچ راهی وجود ندارد
صفحه‌ی `/forgot` پیام «ایمیل بازیابی ارسال شد» نشان می‌دهد ولی هیچ کاری نمی‌کند؛ هیچ API‌ای برای ریست رمز توسط مدیر هم وجود ندارد
(فقط تغییر رمز با داشتن رمز فعلی). اگر مدیر کل رمزش را فراموش کند، فقط با دست‌بردن در دیتابیس. صفحه‌ی `/signup` هم فرم کاملی است که
آخرش می‌گوید «ثبت‌نام فعال نیست».

### 🟠 M13 — استخدام: فایل‌ها داخل دیتابیس
رزومه و فایل‌ها به‌صورت base64 (تا ۸MB) داخل ردیف دیتابیس ذخیره می‌شوند؛ `customFields` عمومی سقف حجم ندارد؛ فهرست متقاضیان
`customFields` را برمی‌گرداند (اگر فیلد فایل داشته باشد، صفحه‌ی ۵۰تایی می‌تواند ده‌ها مگابایت شود). با limiter ضعیف (B7)، پرکردن دیتابیس آسان است.

### 🟠 M14 — خطاها
- ۱۷۴ مسیر از ۲۰۴ از `handleError` استفاده می‌کنند که خطای ۵۰۰ را فقط در کنسول چاپ می‌کند، نه در «لاگ سیستم» ← خطاهای production دیده نمی‌شوند.
- `postToBasharaf.ts` پیام‌های فارسی را با `new Error()` می‌اندازد ← کاربر به‌جای «فقط اجرای تأییدشده قابل ثبت است» پیام کلی «خطای داخلی سرور» می‌بیند.
- هر خطای حاوی «violates» (مثلاً NOT NULL) به‌اشتباه به‌عنوان «رکورد ارجاع دارد» گزارش می‌شود.

### 🟠 M15 — سایر موارد متوسط
- **ویرایش تراکنش pending** (`PATCH`) قوانین انتقال را چک نمی‌کند: می‌شود نوع را «انتقال» کرد بدون صندوق مقصد یا با مبدا=مقصد ← تأییدش بی‌صدا هیچ اثری ندارد.
- **بازمحاسبه‌ی موجودی صندوق‌ها** (`/api/accounts/recalculate`) اتمیک نیست؛ تراکنشی که هم‌زمان تأیید شود، بازنویسی و گم می‌شود.
- **تأیید رسید خرید بدون انتخاب صندوق**، بی‌صدا «اولین صندوق فعال» را بدهکار می‌کند.
- **سفارش آنلاین** rate limit ندارد و طول آرایه‌ی `items` سقف ندارد؛ کوپن/وفاداری روی سفارش آنلاین اعمال نمی‌شود (`discount = 0` ثابت).
- **محاسبه‌ی حقوق** (`payroll/runs/[id]/calculate`) وضعیت را بیرون از تراکنش چک می‌کند (هم‌زمانی با تأیید).

### 🟡 جزئی‌ها
- OTP: پیام «۲ دقیقه صبر کنید» ولی در عمل تا ۷ دقیقه بلاک می‌کند (`OTP_SPAM_MS` روی `expiresAt`)؛ کد با `Math.random` ساخته می‌شود (بهتر `crypto.randomInt`).
- رزرو: چک idempotency قبل از قفل است ← درخواست هم‌زمان با همان کلید به‌جای رزرو قبلی خطای ۵۰۰ می‌گیرد؛ `reserveAt` با ساعت سرور ساخته می‌شود؛
  `Intl` با `hour12:false` نیمه‌شب ممکن است «24» برگرداند (بهتر `hourCycle:'h23'`).
- شماره‌ی رسید انبار بر اساس «تعداد برگه‌ها + ۱» ساخته می‌شود (تکراری‌پذیر).
- جدول‌های outbox اعلان، audit، sms_log سیاست پاک‌سازی ندارند (رشد بی‌پایان).
- پوشه‌های دیپلوی قدیمی در ریشه (`v0.9.*`, `v9.1.0`, ~۹MB).
- ۵ هشدار lint قدیمی (`react-hooks/exhaustive-deps`) در form-builder، AddressPicker، useRealtime.

## ۳. پیشنهادها برای سیستم کامل‌تر

1. **بازیابی رمز واقعی:** با پیامک OTP (زیرساخت ملی‌پیامک موجود است) + دکمه‌ی «ریست رمز» برای مدیر کل در تنظیمات تیم.
2. **ابطال نشست:** «خروج از همه‌ی دستگاه‌ها» و ابطال خودکار هنگام غیرفعال‌سازی/تغییر نقش (همراه B2).
3. **حسابداری تعهدی درست:** انبار به‌عنوان دارایی، COGS در سود و زیان، گزارش **جریان نقد** جدا (حل ریشه‌ای B5).
4. **قفل واقعی دوره‌ی مالی** روی همه‌ی مسیرهای ثبت + «بازگشایی» با دلیل و ردپای حسابرسی (M1).
5. **چرخه‌ی کامل چک:** وصول ← تراکنش خودکار و اثر روی صندوق/طرف‌حساب؛ برگشت ← بازگرداندن بدهی؛ یادآور سررسید.
6. **استرداد و تطبیق پرداخت آنلاین:** وضعیت «مسترد شد»، گزارش تطبیق روزانه با درگاه.
7. **تکمیل حساب مشتری آنلاین:** ارسال OTP، اتصال سفارش‌ها، «سفارش مجدد»، و اعمال کوپن/امتیاز وفاداری روی سفارش آنلاین.
8. **پشتیبان‌گیری خودکار روزانه + تمرین بازگردانی**؛ «ریست کارخانه» فقط بعد از بکاپ موفق.
9. **محیط staging** (اپ و دیتابیس دوم روی لیارا): الان هر push روی main مستقیم production است؛ migrationها اول آنجا تست شوند.
10. **پایش:** endpoint سلامت (`/api/health` با چک دیتابیس) + سرویس uptime + اعلان خطا به مدیر.
11. **خروجی برای حسابدار:** خروجی دفتر روزنامه‌ی استاندارد (سند دوبل) از تراکنش‌ها.
12. **صفحه‌ی «سلامت داده» برای مدیر:** نمایش drift صندوق‌ها/طرف‌حساب‌ها/انبار با کوئری‌های بخش ۵، به‌صورت خودکار.
13. **انبار شعبه‌ای برای رسپی سراسری** (M7) اگر شعبه‌ی دوم انبار مستقل بگیرد.

## ۵. کوئری‌های فقط‌خواندنی برای تأیید روی دیتابیس واقعی

> این‌ها فقط `SELECT` هستند و چیزی را تغییر نمی‌دهند — در pgAdmin/DBeaver قابل اجرا.

```sql
-- (الف) drift صندوق‌ها: موجودی ذخیره‌شده در برابر موجودی محاسبه‌شده از تراکنش‌های تأییدشده
SELECT a.name, a.balance AS stored,
  COALESCE((SELECT SUM(CASE WHEN t.type='income' THEN t.amount
                            WHEN t.type IN ('expense','transfer') THEN -t.amount END)
            FROM transactions t WHERE t.status='approved' AND t.account_id=a.id),0)
+ COALESCE((SELECT SUM(t.amount) FROM transactions t
            WHERE t.status='approved' AND t.type='transfer' AND t.destination_account_id=a.id),0) AS computed
FROM accounts a
ORDER BY abs(a.balance - (
  COALESCE((SELECT SUM(CASE WHEN t.type='income' THEN t.amount WHEN t.type IN ('expense','transfer') THEN -t.amount END)
            FROM transactions t WHERE t.status='approved' AND t.account_id=a.id),0)
+ COALESCE((SELECT SUM(t.amount) FROM transactions t
            WHERE t.status='approved' AND t.type='transfer' AND t.destination_account_id=a.id),0))) DESC;

-- (ب) B4: اقلامی که «موجودی نمایشی» با موجودی قطعی فرق دارد (و برگه‌ی pending هم ندارند)
SELECT i.name, i.qty_physical, i.qty_base, i.qty_physical - i.qty_base AS diff
FROM inv_items i
WHERE abs(i.qty_physical - i.qty_base) > 0.001
  AND NOT EXISTS (SELECT 1 FROM inv_voucher_lines l JOIN inv_vouchers v ON v.id=l.voucher_id
                  WHERE l.item_id=i.id AND v.status='pending')
ORDER BY abs(i.qty_physical - i.qty_base) DESC;

-- (پ) M2: تراکنش‌هایی که تاریخشان فرمت استاندارد ندارد
SELECT id, date, title, created_at FROM transactions
WHERE date !~ '^[۰-۹]{4}/[۰-۹]{2}/[۰-۹]{2}$' ORDER BY created_at DESC;

-- (ت) B3: سفارش‌هایی که بیش از یک تراکنش فروش دارند
SELECT sale_meta->>'orderId' AS order_id, count(*) FROM transactions
WHERE type='income' AND sale_meta->>'source'='order' GROUP BY 1 HAVING count(*) > 1;

-- (ث) M1: تراکنش‌های ثبت‌شده در دوره‌های بسته بعد از زمان بستن
SELECT t.id, t.date, t.title, t.created_at, fp.closed_at AS period_closed_at
FROM transactions t JOIN financial_periods fp
  ON t.date LIKE translate(fp.jalali_year::text, '0123456789', '۰۱۲۳۴۵۶۷۸۹') || '/' ||
                 translate(lpad(fp.jalali_month::text, 2, '0'), '0123456789', '۰۱۲۳۴۵۶۷۸۹') || '/%'
WHERE t.created_at > fp.closed_at;
```

> نام ستون‌ها با `lib/db/schema.ts` تطبیق داده شده‌اند.

## ۶. نقاط قوت (برای حفظ‌کردن)

- تأیید تراکنش، تأیید برگه‌ی انبار و تأیید حقوق درست با `SELECT … FOR UPDATE` قفل شده‌اند — الگوی صحیح برای رفع B3.
- رزرو عمومی با قفل میزها از رزرو دوبل جلوگیری می‌کند و ۳۳ تست دارد.
- سفارش آنلاین با `clientToken` idempotent است؛ مبلغ پرداخت همیشه از سرور خوانده می‌شود؛ callback درگاه کد ۱۰۱ (قبلاً تأییدشده) را درست مدیریت می‌کند.
- صف اعلان‌ها با `FOR UPDATE SKIP LOCKED` و retry/backoff درست ساخته شده.
- چاپ فاکتور همه‌ی ورودی‌ها را escape می‌کند؛ هیچ `dangerouslySetInnerHTML` ناامنی پیدا نشد.
- کوکی‌ها httpOnly + SameSite=Lax؛ مقایسه‌ی رمز timing-safe؛ JWT مشتری با کلید جدا.
- موتورهای محاسبه (حقوق ساعتی، costing، VAT، ظرفیت رزرو) خالص و تست‌شده‌اند.
